Demystifying Token Development: Facts vs. Myths on Flashing & Cloning

Published by Solidity Dev • Read Time: 3 mins

I always see posts popping up discussing this, I’ve been deploying tokens and playing around with Solidity for a good while so I figured I’d make a thread to even out some of the facts and myths about flashing.

First off, a lot of people tend to confuse two distinct concepts: flashing and cloning/forking.

Understanding Flashing

Flashing in general, from a development perspective, is simply making a function call (usually a TransferFrom function, if non-OnlyOwner) on an already existing (IERC20 protocol) contract. It essentially means you’re sending out tokens, without actually holding them.

The receiver of these tokens however sees within their wallet the same icon/price as if he’s receiving balance. You don’t need to “add liquidity” or whatever, because the liquidity pairs are (usually) already present with the original token contract.

How it works is every IERC20 needs to have a non-OnlyOwner / (0)Owner TransferFrom function for it to be interact-able by users trying to send the token, because even simply sending a token is an interaction with the token’s smart contract (you can check your own txhash after creating a transaction to see which function your wallet interacted with). With flashing you basically manipulate the TransferFrom function into creating a transaction without your wallet actually holding the tokens balance, you do this by creating a low-GWEI tx.

The Anatomy of Forking & Cloning

Forking/cloning is a whole different side of the spectrum. You’re basically recreating an already existing token, redeploying it, and giving it the same logo & price as the one you’re mimicking.

The logo can be set through explorer APIs, but they won’t allow an exact clone so you need to slightly alter it (they approve stuff algorithmically so it’s pretty easy to circumvent, if you play around with it). Price is pegged by creating a liquidity pair using the chain’s DEX (for example, Uniswap for ERC20s) and playing around with market cap—simple maths.

You can quite easily fork/clone pretty much any token by navigating to their explorer page (by looking up their Contract Address). If their source code is verified on-chain, and not behind a proxy smart contract, you can simply copy the source code directly from the explorer page. Just make sure to alter a couple of constructor lines (or remove unused imports) to make sure your contract doesn’t get flagged with a “similar match” tag after deployment.

Key Takeaway

The main difference between the two is that flashing is visible in wallets without needing to add a custom Contract Address (CA), since it’s recognized as an already established token. Forks/clones usually are not—but they have their own use cases, so one isn’t necessarily better or worse than the other.

Hoping this was helpful in answering some questions and clearing up doubts.
